# 크래시 진단 — 죽은 자리에 이름을 남긴다

**상태:** 설계 확정
**날짜:** 2026-08-19

## 무엇을 바꾸나

"특정 이로치 포켓몬의 상세 화면에 들어가면 죽는다"는 제보를 받았다. 어떤 포켓몬인지, 어느
시점인지 알 수 없다. **지금 있는 로그로는 좁힐 수 없다** — 크래시 순간에 남는 것이 이게 전부다:

```
[CRASH] fatal signal SIGTRAP
```

`CrashReporter` 는 이미 세 겹으로 잘 잡는다(정상종료 마커 · 시그널 핸들러 · NSException). 빠진
것은 **"무엇을 하다 죽었나"** 다. 이 문서는 그 문맥을 남기고, 사용자가 GitHub 이슈로 한 번에
넘길 수 있게 한다.

## 왜 로그에 그냥 못 쓰나 — 이 설계의 제약 둘

**① 시그널 핸들러는 문자열을 만들 수 없다.** async-signal-safe 해야 해서 `write()` 와
`StaticString` 밖에 못 쓴다(`CrashReporter.signalHandler` 주석 참고). 죽는 순간에
`"species=133 shiny=true"` 를 조립하는 것은 불가능하다. **문맥은 죽기 전에 이미 디스크에 있어야
한다.**

**② `AppLog.write` 는 비동기라 못 쓴다.** `queue.async` 로 넘기므로, 상세 화면을 여는 바로 그
런루프에서 죽으면 기록이 도착하기 전이다. 진단이 필요한 정확히 그 순간에 없어진다.

따라서 **동기 write** 가 필요하다. 이것이 이 기능의 유일한 load-bearing 성질이고, 나중에 누가
"성능을 위해" 비동기로 바꾸면 기능 전체가 조용히 죽는다 — **테스트로 잠근다.**

## 1. 빵부스러기 (`Breadcrumbs`)

`Sources/PokeDexBar/Core/Breadcrumbs.swift` (신규)

최근 **20개** 행동을 메모리 링에 담고, 추가될 때마다 작은 파일 하나를 **동기·원자적으로 통째
덮어쓴다.**

- 20줄 × 약 80바이트 ≈ 1.6KB. **회전이 없다** — 덮어쓰므로 안 자란다.
- 원자적 write(`options: .atomic`)라 쓰는 도중에 죽어도 파일이 찢어지지 않는다.
  `CrashReporter` 의 running 마커가 이미 같은 방식을 쓴다.
- 사용자 동작 빈도라 idle CPU 예산과 무관하다. **사용량 틱처럼 자주 도는 자리에는 안 건다** —
  메뉴바 앱의 idle 규율(CLAUDE.md)을 깨지 않기 위해서다.

### 무엇을 남기나

이번 제보를 풀었을 최소한 — **종을 남기는 것이 핵심**이다:

```
detail open: species=133 display=151 form=nil region=nil shiny=true
             level=42 grade=rare disguised=true line=loaded
```

여기에 탭 전환, 부화, 진화, 알 수령, 원정 출발·수령을 더한다. **텔레메트리를 만드는 것이
아니다** — 화면 전환과 상태 전이만 남기고, 매 초 도는 것은 안 남긴다.

### 다음 기동에 합친다

`CrashReporter.install` 이 이미 `drainCrashLog()` 로 crash.log 를 메인 로그에 합치고 비운다.
빵부스러기도 같은 자리에서 합치되, **직전 세션이 비정상 종료였을 때만** 합친다(정상 종료였으면
지우기만 한다). 정상 종료의 빵부스러기까지 매번 남기면 메인 로그가 잡음으로 차서 2MB 회전이
빨라지고, 정작 필요한 이력이 밀려난다.

### 파일 자리 — 테스트가 실제 로그를 오염시키지 않게

`AppLog.write` 는 `AppEnv.isBundledApp` 가드로 테스트의 write 를 막는다. 빵부스러기에 같은
가드를 그대로 걸면 **동기 write 성질 자체를 테스트할 수 없다.**

대신 **기본 경로를 `AppEnv` 로 가른다** — 배포 앱이면 `~/Library/Logs/<storageName>.breadcrumbs`,
아니면 임시 디렉터리. 테스트는 경로를 명시적으로 갈아끼운다. 개발 앱과 배포 앱이 세이브를 나눠
쓰는 것과 같은 원칙이다.

## 2. 진단 정보 (`Diagnostics`)

`Sources/PokeDexBar/Core/Diagnostics.swift` (신규)

한 덩어리의 텍스트를 만든다:

- 앱 버전, macOS 버전
- 직전 세션이 비정상 종료였는지
- 마지막 크래시 줄들
- 빵부스러기 20줄
- 박스 크기·도감 수 같은 규모 정보(개체 내용은 아니다)

### 개인정보 — GitHub 은 공개된 자리다

- **홈 디렉터리 경로를 지운다.** `/Users/<이름>/…` → `~/…`. 로그 곳곳에 사용자 이름이 들어가고,
  그대로 공개 이슈에 붙으면 실명이 샌다. `NSHomeDirectory()` 문자열 치환으로 지운다.
- **세이브 내용은 안 넣는다.** 개체 목록·지갑·토큰 사용량은 진단에 필요 없다.
- **사용자가 붙여넣기 전에 전문을 본다.** 앱이 자동으로 제출하지 않는다 — 이슈 작성 페이지를
  열어 줄 뿐이고, 보내기는 사용자가 누른다. 지금 `SupportMail` 이 메일을 직접 안 보내고 mailto
  만 여는 것과 같은 원칙이다.

## 3. GitHub 이슈로 넘기기

`https://github.com/donky-ey/PokeDexBar/issues/new?title=…&body=…` 를 조립해 브라우저로 연다.

**길이를 잘라야 한다.** URL 은 실무상 8KB 안쪽이 안전한데, 한글은 percent-encoding 으로 세 배가
된다. **인코딩된 최종 URL 이 6,000자를 넘지 않게** 빵부스러기와 크래시 줄을 뒤에서부터 자르고,
잘렸으면 본문에 그 사실과 "설정 → 로그 파일 보기" 안내를 남긴다. 자르고도 **앱 버전과 비정상
종료 여부는 반드시 남는다** — 그 둘이 없으면 이슈가 무의미하다.

**"진단 정보 복사"** 를 함께 둔다. 자르지 않은 전문을 클립보드에 넣으므로, 이슈가 잘렸거나
사용자가 다른 데(디스코드·메일)에 붙이고 싶을 때의 탈출구가 된다.

## 4. 화면

설정의 `aboutSupportGroup` 을 고친다. 지금은 "문제점 알리기"(메일) 한 줄 + "로그 파일 보기" 한
줄이다. 바뀐 뒤:

| 줄 | 컨트롤 |
|---|---|
| 문제 제보 | `[GitHub]` `[진단 정보 복사]` |
| 로그 파일 보기 | `[Finder]` |

**메일 경로(`SupportMail`)는 지운다.** 사용자가 창구를 GitHub 으로 정했고, 쓰이지 않는 경로를
남기지 않는다(CLAUDE.md 원칙 2). 지워지는 것: `Core/SupportMail.swift`, `L.reportMailSubject`·
`reportMailBody`·`reportMailFallback`, 그리고 `SettingsView.reportProblem`. 비공개로 알리고 싶은
사용자를 위한 주소는 GitHub 프로필에 이미 공개돼 있다.

브라우저 열기에 실패하면 지금의 `reportError` 자리에 이슈 URL 을 **선택 가능한 텍스트**로 띄운다
(지금 메일 폴백이 주소를 그렇게 띄운다).

좁은 자리라 **렌더해서 확인한다** — 한 줄에 버튼 두 개가 들어가고 세 언어에서 안 깨지는지.

## 5. 이 제보에 대해 알아낸 것

**이로치는 미끼일 가능성이 있다.** 이로치 전용 경로를 전수로 봤고 전부 방어돼 있다 — 반짝임
연출(`SparkleSpec.ring` 은 `count > 0` 가드), 이로치 스프라이트 요청(미제공 종이면 일반으로
폴백), 방출 확인 단계, 사탕 버튼. 강제 언래핑도 없다. 스프라이트 잘라내기·확대
(`SpriteTrim`·`PixelUpscaler`)의 픽셀 연산도 0 나누기와 빈 사각형을 막아 뒀다.

특정 **종**에서 죽는 것이라면 사용자에게는 "그 이로치를 누르면 죽는다"로 보인다 — 자기 박스에서
그 종이 하필 이로치 한 마리뿐이기 때문이다. **그래서 빵부스러기가 남겨야 하는 것은 이로치
여부가 아니라 종·폼·지방·라인 상태다.** §1 의 형식이 그렇게 잡혀 있다.

**따로 발견한 것:** `SpriteLoader.swift:146` 의
`FileManager.default.urls(for: .applicationSupportDirectory, in: .userDomainMask)[0]` 는 빈
배열이면 죽는다. 이번 건과는 무관해 보이지만 같은 부류(크래시 가능 지점)라 함께 고친다 —
같은 패턴을 코드베이스에서 전수로 훑는다(CLAUDE.md 결함 대응 §2 부류 스윕).

## 6. 테스트

**동기 write** — `Breadcrumbs.record(...)` 가 **돌아온 직후** 파일에 그 줄이 있는지. 이 기능이
존재하는 이유이고, 비동기로 바뀌면 조용히 죽는 유일한 성질이다. **돌연변이 확인 필수**:
write 를 `queue.async` 로 바꿔 보고 이 테스트가 실패하는지 본다.

**링 버퍼** — 20개를 넘으면 오래된 것부터 빠지고 최근 20개가 남는지. 21개를 넣어 첫 줄이
사라졌는지 확인한다.

**경로 지우기** — `/Users/someone/Library/...` 가 `~/Library/...` 로 바뀌는지. **대조군:**
경로가 아닌 텍스트(`species=133`)는 그대로 남는지. 지우기가 너무 넓게 잡히면 진단이 통째로
뭉개진다.

**URL 길이** — 빵부스러기를 가득 채운 상태에서 조립한 URL 이 6,000자 이하이고, 여전히 유효한
`URL` 이며, **앱 버전과 비정상 종료 여부가 남아 있는지.** 자르기가 앞부분을 먹으면 안 된다.

**잘림 표시** — 실제로 잘렸을 때만 본문에 안내가 붙고, 안 잘렸으면 안 붙는지(양쪽 다).

**합치기 게이트** — 비정상 종료 뒤 기동에는 빵부스러기가 메인 로그로 합쳐지고, **정상 종료 뒤
기동에는 안 합쳐지는지**(대조군).

**화면 배선** — 두 버튼이 실제로 화면에 있고 **눌렀을 때 실제로 동작하는지**(`#if DEBUG`
레코더). 이 레포는 "상점에서 팔리는데 쓸 화면이 없던" 결함을 겪었고 `SettingsToggleRow` 가
그것 때문에 별도 타입으로 뽑혀 있다 — 같은 부류를 여기서도 막는다.

**상세 화면 진입이 실제로 빵부스러기를 남기는지** — 화면을 호스팅해 개체를 열고, 파일에 그
종 번호가 찍혔는지 확인한다. 기록 함수만 직접 부르는 테스트는 배선이 끊겨 있어도 통과한다.

## 안 하는 것

- **자동 전송.** 앱이 사용자 모르게 아무것도 안 보낸다.
- **원격 크래시 수집 서비스.** 외부 의존성을 안 더한다(CLAUDE.md).
- **스택 트레이스 수집.** macOS 가 이미 `.ips` 로 남기고 `CrashReporter` 가 그 위치를 안내한다.
- **텔레메트리.** 사용 패턴·시간·빈도를 안 모은다. 빵부스러기는 **크래시 직전 문맥**만이다.
- **이로치 크래시 자체의 추측 수정.** 원인을 모른 채 고치면 고쳤는지도 알 수 없다. 이 기능이
  다음 제보에서 종 번호를 찍어 주면 그때 고친다.
