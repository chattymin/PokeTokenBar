# 박스 정리 — 한 번 누르면 다시 배열된다

**상태:** 설계 확정, 구현 전
**날짜:** 2026-08-13

## 무엇을 바꾸나

박스는 지금 화면을 그릴 때마다 `obtainedAt` 으로 다시 정렬한다(`BoxTabView.sorted`). 저장된
배열 순서는 아무도 안 본다.

이 문서는 그걸 뒤집는다. **저장된 순서가 곧 화면 순서**가 되고, 정렬은 그 저장된 순서를
**한 번 재배치하는 명령**이 된다.

## 확정된 결정 (사용자)

1. 정렬은 **보기가 아니라 동작**이다. 누른 그 시점에 한 번 재배치되고, 그 결과가 저장된다.
2. **새로 생긴 개체는 언제나 맨 뒤.** 정렬 기준에 맞는 자리에 끼워 넣지 않는다.
3. 항목은 여섯 축 — 획득순 · 레벨 · 등급 · 도감번호 · 이로치 · 리본.

## 1. 저장된 순서를 그린다

`BoxTabView.sorted` 를 없애고 `store.state.box` 를 그대로 그린다.

기존 세이브는 이미 삽입 순서(=획득 순서)로 저장돼 있으므로 **마이그레이션이 없다.** 지금
화면과 첫 배치가 똑같다.

**딸려 오는 것:** 지금은 개체가 진화해도 화면 자리가 안 변한다(`obtainedAt` 이 안 변하므로).
저장 순서를 그려도 같다 — 진화는 `state.box[index]` 를 제자리에서 고치기 때문이다. 껍질몬만
`append` 로 맨 뒤에 서는데, 그것이 결정 2 그대로다.

## 2. 정렬 — 일곱 개의 명령

```swift
enum BoxSort: String, CaseIterable {
    case obtained          // 획득순 (되돌리기)
    case levelHigh, levelLow
    case grade             // 레전더리부터
    case dex               // 도감번호 낮은 것부터
    case shiny             // 이로치 먼저
    case ribbon            // 높은 리본부터
}
```

**왜 방향을 항목으로 나누나:** 명령이므로 "다시 누르면 뒤집힘"은 성립하지 않는다 — 같은 이름의
버튼이 누를 때마다 다른 일을 하게 된다. 양방향이 실제로 쓸모 있는 것은 레벨뿐이라(높은 순 =
키운 것 보기, 낮은 순 = 보낼 것 찾기) 그것만 둘로 나눈다.

**획득순은 항상 있어야 한다.** `obtainedAt` 은 개체마다 그대로 남으므로 이 항목이 **유일한
되돌리기**다. 정렬이 파괴적인 동작인데 되돌릴 길이 없으면 안 된다.

### 정렬 함수

`BoxSort.apply(to box: [Individual], at now: Date) -> [Individual]` — 순수 함수. 스토어는 그
결과를 `state.box` 에 넣고 저장한다.

**`now` 를 받는 이유:** 리본은 함께한 시간에서 파생되므로(`Individual.ribbon(at:)`) 시계가 있어야
읽을 수 있다. 순수 함수로 두려면 시계를 인자로 받아야 하고, 그래야 테스트가 결정적이 된다.

**동률은 `obtainedAt` → `id` 로 떨어뜨린다.** 이차 키가 없으면 같은 등급 40마리의 배치가
호출마다 달라지고, 이제 그 배치가 **디스크에 저장되므로** 열 때마다 박스가 뒤섞인 것처럼 보인다.
`id`(UUID)까지 가는 이유는 `obtainedAt` 도 동률일 수 있어서다 — 같은 정산에서 사탕이 여러 개
나오듯, 한 순간에 둘이 들어오는 경로가 있다.

| 항목 | 1차 키 | 방향 |
|---|---|---|
| 획득순 | `obtainedAt` | 오래된 것부터 |
| 레벨 높은 순 | `level` | 내림 |
| 레벨 낮은 순 | `level` | 오름 |
| 등급 | `grade` | 레전더리부터 |
| 도감번호 | **`displaySpeciesID`** | 오름 |
| 이로치 | `showsShiny` | 이로치 먼저 |
| 리본 | `ribbon(at:)` | 높은 것부터, **리본 없음은 맨 뒤** |

### 도감번호는 `displaySpeciesID` 여야 한다

메타몽은 뮤로 위장한 채 박스에 앉아 있다(`Individual.disguisedAs`). 진짜 `speciesID`(132)로
정렬하면 뮤로 보이는 아이가 **132번 자리에** 서서, 눌러 확인하기 전에 정체가 샌다. 화면에 보이는
번호(`displaySpeciesID`)로 정렬해야 위장이 유지된다. 이로치도 같은 이유로 `showsShiny` 를
쓴다(위장 중이면 이로치를 감춘다).

**테스트로 잠근다** — 눈으로는 절대 안 걸리는 부류다.

## 3. 화면

박스 헤더는 `[◀][▶] … 제목 … [선택]` 이고 이미 한 번 갈아엎은 자리다(칩 위치를 두 번 고쳤다).
**선택 칩 왼쪽**에 아이콘만 있는 정렬 메뉴(`arrow.up.arrow.down`)를 단다. 현재 정렬 상태를
표시하지 않는다 — 상태가 아니라 명령이므로 표시할 것이 없다.

좁은 자리라 **렌더해서 확인한다.** 제목이 밀리거나 선택 모드에서 겹치면 배치를 다시 잡는다.

**선택 모드와 안 부딪힌다** — 선택은 `Set<UUID>` 라 재배치돼도 그대로 따라간다. 다만 정렬 중
선택이 유지되는지는 테스트로 확인한다.

## 5. README·랜딩

README 두 곳과 랜딩이 *"sorted oldest-first, so a slot never moves once it's filled"* 라고
약속하고 있고, **칸에 이름표가 없는 근거가 그 약속**이다. 정렬이 자리를 옮기므로 고친다:

> 획득 순서로 쌓이고, **직접 정리하기 전까지는** 자리가 안 움직인다.

위치로 기억한다는 설계는 그대로 산다 — 자리가 바뀌는 건 사용자가 명시적으로 누를 때뿐이다.
en/ko/ja 세 언어와 랜딩 i18n 사전(키 정합)까지 함께 고친다.

## 6. 테스트

**정렬 자체(순수 함수)** — 일곱 항목이 각각 기대한 순서를 내는지. 각 항목마다 **그 축에서만
갈리는 픽스처**를 쓴다(등급 테스트에서 레벨까지 다르면 무엇이 정렬했는지 알 수 없다).

**동률 안정성** — 같은 축이 같은 개체 여럿을, 같은 입력으로 두 번 정렬해 **같은 배치**가 나오는지.
그리고 동률이 `obtainedAt` 순으로 떨어지는지.

**위장** — 위장한 메타몽이 도감번호순에서 **표시 번호(뮤) 자리**에 서는지. 이로치 정렬에서도
위장 중이면 이로치로 안 세는지.

**저장** — 정렬한 뒤 재시작해도 그 배치가 남는지. 그리고 **정렬 뒤에 들어온 개체가 맨 뒤에
붙는지**(결정 2 — 정렬 기준 자리에 끼면 안 된다).

**되돌리기** — 아무 정렬이나 한 뒤 획득순을 누르면 원래 배치로 돌아오는지.

**선택 유지** — 선택 모드에서 몇 마리를 고른 뒤 정렬해도 그 선택이 유지되는지.

**화면 배선** — 메뉴 항목을 실제로 누르면 `state.box` 가 재배치되는지(`#if DEBUG` 레코더).

## 안 하는 것

- **필터.** 성격·지방·태생폼으로 걸러 보는 건 다른 기능이고, 정렬로 대신할 수 없다. 필요해지면
  따로 설계한다.
- **정렬 기준 저장.** 저장할 것이 없다 — 재배치된 `state.box` 자체가 결과다.
- **수동 드래그 재배치.** 정렬 명령으로 충분한지 먼저 본다.
- **박사에게 보내는 값 순.** 후보였으나 사용자가 뺐다. 레벨 낮은 순이 실질적으로 그 일을 한다.
