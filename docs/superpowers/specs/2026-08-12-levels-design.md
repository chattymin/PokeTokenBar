# 레벨 — 경험치를 본가 체계로

**상태:** 설계 확정, 구현 전
**날짜:** 2026-08-12

## 무엇을 바꾸나

지금 `Individual.exp` 는 **쓴 토큰 수 그 자체**이고, 진화 임계와 알 임계를 겸한다. 화면에는
"경험치 12,300,000 / 50,000,000" 같은 값이 뜬다. 포켓몬을 키우는 앱인데 정작 그 수는 포켓몬의
것이 아니다.

이 문서는 그것을 **본가의 경험치·레벨 체계**로 바꾼다. 레벨 1~100, 6가지 실제 성장 곡선, 실제
`min_level` 진화. 그리고 그 과정에서 **알을 경험치에서 떼어낸다** — 지금 등급이 경험치에
끼어들어야 했던 유일한 이유가 알이었기 때문이다.

## 확정된 결정 (사용자)

1. 진화는 **실제 `min_level` 그대로**. 파이리는 16레벨에 리자드가 된다.
2. **알과 경험치를 분리**한다. 알은 자기 계량기를 갖는다.
3. 알 계량기는 **파트너인 동안** 찬다 — 최종진화 조건은 없어진다.

## 1. 성장 곡선 — `GrowthRate`

`Sources/PokeDexBar/Player/GrowthRate.swift` (신규)

```swift
enum GrowthRate: String, Codable, Sendable, CaseIterable {
    case erratic, fast, mediumFast, mediumSlow, slow, fluctuating
}
```

PokéAPI `pokemon-species.growth_rate.name` 매핑 — **이 여섯이 전부다**(PokéAPI 의 growth-rate
리소스가 여섯 개다):

| PokéAPI | `GrowthRate` |
|---|---|
| `slow-then-very-fast` | `erratic` |
| `fast` | `fast` |
| `medium` | `mediumFast` |
| `medium-slow` | `mediumSlow` |
| `slow` | `slow` |
| `fast-then-very-slow` | `fluctuating` |

모르는 문자열은 `mediumFast` 로 떨어뜨린다(§6 참조 — 데이터가 늦게 와도 화면이 멈추면 안 된다).

### 누적 경험치 공식

`totalExp(at level: Int) -> Int`. 본가 공식 그대로이며 **정수 내림**이다. `level <= 1` 이면 0
(mediumSlow 공식은 n=1 에서 음수가 나온다 — 특수 처리하지 않으면 레벨 계산이 깨진다).

```
erratic       n < 50:  n³(100−n)/50
              n < 68:  n³(150−n)/100
              n < 98:  n³·⌊(1911−10n)/3⌋/500
              n ≤ 100: n³(160−n)/100
fast                   4n³/5
mediumFast             n³
mediumSlow             1.2n³ − 15n² + 100n − 140
slow                   5n³/4
fluctuating   n < 15:  n³·(⌊(n+1)/3⌋+24)/50
              n < 36:  n³·(n+14)/50
              n ≤ 100: n³·(⌊n/2⌋+32)/50
```

100레벨 도달치 — 이 값들이 맞으면 곡선 전체가 맞다고 봐도 된다(테스트 고정값):

| | L100 EXP |
|---|---|
| erratic | 600,000 |
| fast | 800,000 |
| mediumFast | 1,000,000 |
| mediumSlow | 1,059,860 |
| slow | 1,250,000 |
| fluctuating | 1,640,000 |

### 레벨 구하기

`level(forExp:) -> Int` — 1…100 을 훑어 `totalExp(at:) <= exp` 인 최대 레벨. 100이 상한이고
그 위로는 경험치를 더 쌓지 않는다(§4의 상한과 같은 이유 — 갈 곳 없는 수가 계속 커지면
화면이 거짓말을 한다).

두 함수는 순수하며 서로의 역이다. 왕복 테스트로 잠근다.

## 2. 환율 — 500토큰 = 1EXP

`ExpBalance.tokensPerExp = 500`. **등급은 경험치에 관여하지 않는다.**

이 값을 500으로 잡은 근거: 실제 사용 로그에서 하루 평균 3.65억 토큰(활동일 22일 기준). 그러면
`mediumFast` 한 마리를 만렙까지 올리는 데 5억 토큰 ≈ **1.5일**이 걸린다. 파트너를 바꿔 가며
키우는 리듬으로 적당하고, 아래 표처럼 성장 타입 차이가 체감된다.

| 성장 타입 | L100 토큰 |
|---|---|
| erratic | 3.0억 |
| fast | 4.0억 |
| mediumFast | 5.0억 |
| mediumSlow | 5.3억 |
| slow | 6.25억 |
| fluctuating | 8.2억 |

레전더리는 실측상 거의 전부 `slow` 다(뮤츠·루기아·레쿠쟈·디아루가·무한다이나·테라파고스 확인).
즉 등급을 안 써도 레전더리가 커먼보다 25% 더 걸린다. **경제의 큰 싱크는 등급이 그대로 쥐고
있는 알(§4)이므로**, 여기서 등급을 또 곱할 이유가 없다.

경험치 부적은 그대로 2배다(`PlayerStore.expGain`) — 곱하는 대상이 토큰에서 EXP 로 바뀔 뿐이다.

## 3. 진화 — 실제 `min_level`

### 파싱

`EvolutionDetail` 에 `min_level: Int?` 를 더한다. `PokeAPIClient.requirement(from:)` 의 우선순위는
**지금 그대로**(도구 → 통신교환 → 친밀도), 마지막 폴스루만 바뀐다:

```swift
// 지금:  return .none
// 바뀜:  return .level(details.compactMap(\.min_level).min() ?? EvoBalance.unstatedLevel)
```

`EvoRequirementRaw`·`EvoRequirement` 에 `case level(Int)` 를 더한다. 뿌리 노드는
`evolution_details` 가 비어 있어 지금처럼 `.none` 이다(뿌리는 무언가로 *진화해 들어오지* 않으므로
조건을 물을 일이 없다).

**`min_level` 이 없는 갈래**(장소·기술·시간·애정처럼 이 앱에 대응물이 없는 조건)는
`EvoBalance.unstatedLevel = 20` 으로 떨어진다. 이건 본가 값이 아니라 **이 앱의 손잡이**이고,
그 사실을 주석과 테스트에 남긴다. 20인 이유는 본가에서 조건 없는 레벨업 진화가 대체로 그 언저리에
있어서다. 막지 않는 것(=1레벨 진화)은 답이 아니다 — 그러면 그 종들만 갓 태어나서 진화한다.

`EvoLine` 은 **메모리 캐시뿐**이라(`PokeAPIClient.lineCache`) 디스크 마이그레이션이 없다.

### 판정

`meetsRequirement` 에 한 줄이 는다:

```swift
case .level(let n): individual.level >= n
```

그리고 **경험치 임계 검사는 통째로 없어진다.** `canEvolve(_:)` 는 라인 없이 판단할 수 없게 되므로
(대상 종의 `min_level` 이 필요하다) `canEvolve(_ individual:, to speciesID:, line:)` 로 바뀐다 —
"갈 수 있는 종이고 그 조건을 만족하는가" 하나로 합쳐진다. 배지를 띄우는 화면은 이미 라인을 갖고
있다(`IndividualDetailView`·`BoxTabView` 모두 `lines` 를 받는다).

**도구·친밀도 갈래는 레벨을 안 본다** — 본가가 그렇다. 갓 부화한 피카츄에 천둥의돌이 있으면
라이츄가 된다. 도구는 파트너로 오래 둬야 물어 오므로(`ribbonForageRate`) 그 자체가 이미 값이다.

### 진화해도 경험치는 안 깎인다

지금은 `exp = exp - threshold` 로 초과분만 이월한다. **없어진다.** 본가에서 진화는 레벨을
되돌리지 않는다. 레벨은 개체의 나이지 다음 단계까지의 잔여가 아니다.

## 4. 알 — 자기 계량기

`Individual.eggProgress: Int = 0` (신규). **파트너인 동안** 쓴 토큰만큼 찬다 — 단위는 EXP 가
아니라 **토큰 그대로**다(임계가 토큰 단위이므로 환산할 것이 없다).

**부적은 안 받는다.** 경험치 부적은 경험치에, 행운의 부적은 재화에 걸린다. 알 진행분은 둘 다
아니다. 이것은 **지금 대비 알 부적 보유자에게 불리한 변화**다 — 지금은 경험치 부적이 `exp` 를
2배로 불려 알까지 두 배로 빨리 찼다. 분리의 대가이며, 부적의 설명("경험치가 2배")과 실제
동작이 처음으로 일치하게 된다.

- 임계는 **지금 값 그대로**: `ExpBalance.eggThreshold(grade:)` = 5억 / 10억 / 20억 / 40억.
- 임계에서 **멈춘다**(지금 `exp` 상한과 같은 이유 — 안 멈추면 안 열어 본 사이에 알이 여러 개
  예약돼 받는 것이 결정이 아니라 밀린 수령이 된다).
- 알을 받으면 0으로(`takeFoundEgg`).
- **최종진화 조건은 없어진다.** 파트너면 된다.
- 알의 종은 지금과 같다 — 그 개체 라인의 뿌리(`Individual.baseID`). 리자몽 파트너는 파이리 알을,
  파이리 파트너도 파이리 알을 부른다.

경험치와 알은 같은 토큰 흐름에서 **나란히** 찬다. 서로를 깎지 않는다 — 그것이 "분리"의 뜻이다.

부수 효과: 첫 알까지가 지금보다 **약 30% 빨라진다**. 예전에는 진화가 경험치를 깎아 먹어서
커먼 기준 실질 7억 토큰이 필요했는데(5억 + 진화 2단계 2억), 이제 5억이면 된다. 의도한 완화다 —
최종진화 게이트가 없어진 만큼 알이 더 흔해지는 게 아니라, **파트너로 두는 시간이 곧 알**이 된다.

## 5. 딸려 바뀌는 것

### `ReleaseBalance` — 박사에게 보내는 값

지금은 `exp / threshold` 비율(0…1 clamp)을 단계 수에 더한다. **레벨로 바꾼다**:

```swift
// 지금:  points = base × (stageIndex + 1 + expRatio)
// 바뀜:  points = base × (stageIndex + 1 + level/100)
```

100레벨이 한 단계를 통째로 더 얹는 것과 같아, 지금과 자릿수가 같고 뜻은 더 분명하다
("얼마나 키웠나"가 곧 레벨이다).

### 경험치 사탕

`PlayerStore+Shop.expCandyAmount`(=1억 토큰)는 지금 토큰 단위다. **EXP 단위로 옮긴다.** 값은
`ExpBalance.candyExp = 200_000` — 1억을 500으로 나눈 값이라 **사탕의 값어치는 안 바뀐다**.

부수 효과 하나가 생기는데 이건 본가와 같아서 오히려 맞다: 곡선이 위로 갈수록 가팔라지므로
**같은 사탕이 저레벨에서는 여러 레벨을, 고레벨에서는 한 레벨도 못 올린다**. `mediumFast` 기준
갓 부화한 개체는 한 알에 L58 까지 가지만, L90 개체는 한 알에 두 레벨이 안 오른다.

### 화면

- **상세**: "경험치 12.3M / 50M" → **`Lv.47` + 다음 레벨까지 남은 EXP 바**. 알 진행 바는 그
  아래 별도 줄(파트너일 때만).
- **박스 칸**: 이름 옆에 `Lv.47`.
- **홈 파트너 카드**: 상단 진행 바가 레벨 진행도. 알 발견 알림은 지금 그대로.
- **진화 가능 배지**: 판정만 바뀌고 표시는 그대로.
- 문구는 ko/en/ja 세 언어(`L.t`).

## 6. 성장 타입은 개체가 들고 다닌다

`Individual.growthRate: GrowthRate = .mediumFast` (신규, 부화·제안·스타터에서 확정).

**왜 라인이 아니라 개체인가:** 레벨 계산은 사용량 갱신 경로(`PlayerStore.update`)에서 매번
일어나는데 그 자리에는 `EvoLine` 이 없다 — 현재 코드가 주석으로 명시하고 있다("여기는 사용량
갱신 경로라 라인이 없다"). 성장 타입을 개체에 심으면 레벨은 **네트워크 없이 항상** 계산된다.
성격·등급과 같은 취급이다.

값의 출처는 `pokemon-species.growth_rate` — **이미 받고 있는 응답**이다(`SpeciesDTO`). `BaseSpecies`
에 `growthRate` 를 더하고, `base-index.json` 스냅샷도 같이 는다. 스냅샷 버전을 올려 옛 캐시가
`mediumFast` 로 굳지 않게 한다.

진화하면 새 종의 성장 타입으로 갱신한다(라인이 있는 자리다). 라인이 아직 없으면 그대로 둔다 —
같은 계열은 성장 타입이 같은 것이 보통이라 실질 오차가 없고, 다음 진화 때 맞춰진다.

## 7. 기존 세이브 이전

`PlayerState.init(from:)` 이 아니라 **개체 단위**(`Individual` 디코딩)에서 한다. 판정 근거는
"`eggProgress` 키가 없다" = 레벨 이전의 세이브다.

```
eggProgress = 기존 exp                       // 쌓아 둔 알 진행분을 안 뺏는다
exp         = min(cap, 기존 exp / 500)        // 토큰 → 실제 EXP, cap = totalExp(at: 100)
growthRate  = .mediumFast                    // 라인이 오면 갱신
```

- 그 자리에서 진화 가능해지는 개체가 많이 생긴다. **이미 쓴 토큰이라 돌려주는 것이 맞다.**
- `exp` 는 진화할 때마다 깎여 왔으므로 "마지막 진화 이후 진행분"이다. 그걸 그대로 EXP 로 읽으면
  실제보다 낮게 잡히지만, 낮게 잡히는 쪽이 안전하다(레벨이 갑자기 100이 되는 것보다 낫다).
- `eggProgress` 에 기존 `exp` 를 그대로 넣는 것은 **관대한 쪽**이다. 알 임계에서 상한이 걸려
  있었으므로 최대 그 등급의 임계값이고, 넘칠 수 없다.

값 범위 검증은 관대 디코딩의 짝으로 함께 둔다(CLAUDE.md) — `exp` 는 `0…totalExp(at:100)`,
`eggProgress` 는 `0…eggThreshold(grade:)` 로 자른다. 둘 다 산술에 쓰이는 수치다.

## 8. 테스트

**곡선** — 여섯 타입의 L1/L16/L36/L50/L100 을 본가 표와 대조(위 100레벨 표 포함). `level(forExp:)`
왕복(모든 타입 × 1…100). `mediumSlow` L1 이 0인지(공식이 음수를 내는 자리).

**환율** — 500토큰 = 1EXP 가 `update` 경로에서 실제로 적용되는지, 경험치 부적이 2배인지.

**진화** — `min_level` 파싱(실제 PokéAPI 응답 모양으로), 우선순위가 안 바뀌었는지(도구 →
통신교환 → 친밀도 → 레벨), `min_level` 없는 갈래가 `unstatedLevel` 로 떨어지는지, 레벨이
모자라면 못 하고 채우면 되는 **양쪽**, 도구 갈래가 레벨을 안 보는지, **진화 후 경험치가 안
깎이는지**.

**알** — 파트너면 최종진화가 아니어도 찬다, 파트너가 아니면 안 찬다, 임계에서 멈춘다, 받으면
0이 된다, 그리고 **경험치와 알이 서로 안 건드린다**(진화해도 `eggProgress` 불변 / 알을 받아도
`exp` 불변) — 이게 이 설계의 핵심 주장이라 대조군까지 둔다.

**이전** — 구 세이브 JSON 에서 레벨과 알 진행분이 **둘 다** 살아나는지, 대조군으로 신규 세이브가
영향을 안 받는지.

**화면** — 상세에 레벨이 실제로 그려지는지(렌더 테스트), 세 언어 문구가 다 차 있는지.

## 안 하는 것

- **개체값·노력치·능력치.** 이 앱에 전투가 없다. 레벨은 "얼마나 키웠나"의 눈금이지 강함의
  지표가 아니다.
- **레벨업 알림.** 100번 뜬다.
- **등급을 경험치에 다시 끼워 넣기.** 싱크는 알이 쥔다.
- **성장 타입별 사탕 보정.** 사탕은 EXP 를 주고, 곡선이 알아서 다르게 반응한다.
